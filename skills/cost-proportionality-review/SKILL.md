# 비용-목적 비례성 점검 (Cost Proportionality Review)

## 핵심 질문

**이 설계의 비용 구조가 실제 사용 목적·빈도에 비례하는가?**

"동작은 하지만 비용이 목적 대비 과도한" 설계는 대부분 사후에(사용량이 쌓이고 나서, 혹은 청구서를 보고서야) 발견된다. 이 스킬은 그걸 설계 단계에서 먼저 걸러내기 위한 체크리스트다. `brainstorming` 스킬의 "Propose 2-3 approaches" / "Presenting the design" 단계에서, 설계가 아래 4개 카테고리 중 하나라도 건드리면 통과시킨다.

## 언제 쓰는가

- 새 API 엔드포인트/쿼리 설계
- DB 스키마·읽기 패턴 설계 (RTDB, Firestore, SQL 무관)
- 스케줄러·크론·헬스체크·폴링 등 상시/주기 실행 설정
- 외부 유료 API(LLM, OCR, 결제, 지도 등) 연동 설계
- 신규 기능의 UI/데이터 모델 정교함을 정할 때

## 체크리스트

### 1. DB/스토리지 읽기

- [ ] 이 데이터가 **자주 안 바뀌는 데이터**(과거 확정 날짜, 마스터/설정 데이터, 마진율 같은 참조값)인가? → 그렇다면 캐시 후보. "일단 만들고 나중에 최적화"가 아니라 처음부터 캐시를 설계에 포함시킬 것.
- [ ] 루프 안에서 노드/레코드를 **하나씩 개별 조회**하는가 (N+1 패턴)?
- [ ] 노드/테이블 **전체를 로드한 뒤 애플리케이션에서 필터링**하는가, 아니면 인덱스·쿼리로 필요한 범위만 좁혀 읽는가?
- [ ] 캐시를 추가한다면, **무효화 범위가 실제로 변경된 범위만큼 정확히 좁혀져 있는가**? (범위를 넓게 잡으면 캐시가 있으나 마나 해진다)

### 2. 상시가동 인프라

- [ ] 스케줄러/폴링의 **실행 빈도가 실제로 필요한 빈도보다 과도한가**? (예: 실제로는 하루 몇 번이면 되는데 매분 실행)
- [ ] `min-instances`/always-on 설정이 **실제 트래픽 패턴**(업무시간 외 유휴 등)과 맞는가?
- [ ] "내리는(scale-down) 동작 자체가 새 배포/리비전을 만들어서 인스턴스를 다시 깨우는" 것 같은 **자기모순적 설정**은 없는가?

### 3. 외부 유료 API

- [ ] 정확도·안정성을 위한 **중복 호출**(병렬 투표, 재시도)이 실제 요구 정확도 대비 과도한 배수는 아닌가?
- [ ] 재시도 정책에 **상한**이 명확히 있는가?

### 4. 기능 규모 대비 실사용

- [ ] 이 기능의 **설계 정교함(세분화된 옵션, 촘촘한 시간 단위 등)이 예상 실사용 빈도와 비례**하는가? 정교하게 만들었는데 실제로는 드물게 쓰일 기능이라면, 단순화가 유지비용을 줄인다.

## 실사고 근거 (kuru / sabakeru, 실측)

| 유형 | 사례 | 결과 |
|---|---|---|
| DB 읽기 — 안 바뀌는 데이터 재조회 | kuru_asp_server KD-219: 마진율 맵을 매 요청마다 재조회 | 캐시 후 RTDB 다운로드 1.35GB/일 절감 |
| DB 읽기 — 마스터 데이터 재조회 | kuru_asp_server KD-220: HQ 마스터 데이터 매번 재조회 | 버전 키 캐시 후 76% 절감 |
| DB 읽기 — 과거 확정 데이터 재조회 | kuru_asp_server KD-222: 일자별 영수증/주문 노드 매번 재조회 | 캐시 후 주간 74% 절감 |
| 캐시 무효화 범위 오류 | kuru_asp_server KD-227: 무효화 범위를 "센터 전체"로 과도하게 잡음 | "실제 쓴 날짜만"으로 축소 — 캐시를 만들어도 무효화 설계가 틀리면 무의미하다는 반례 |
| 상시가동 인프라 | sabakeru/yamaharu: 매분 실행 스케줄러가 4vCPU/16Gi 서버를 24/7 warm 유지 | 월 비용 2.2배 증가, 원인 규명까지 수 주 소요 |
| 자기모순 설정 | sabakeru/yamaharu: scale-down 잡이 `min-instances=0`으로 새 리비전을 생성 → 배포 자체가 인스턴스를 깨움 | "내리려는 행위가 인스턴스를 띄우는" 역설, 실측 검증 후에야 발견 |
| 외부 유료 API 중복 호출 | sabakeru OCR: 정확도 위해 Gemini Pro를 매 OCR마다 3중 병렬 호출(vote=3) | 토큰 비용 3배 — 의도된 설계였으나 비용 대비 재검토 후보로 티켓화 |
| 기능 규모 대비 실사용 | yamaharu 단가 변경 예약: UI를 30분 격자 단위로 정교하게 설계 | 실사용 5건뿐 — 정교함이 실사용과 비례하지 않은 사례 |

## 적용 방법

`brainstorming` 단계에서 설계를 제시하기 전에 위 체크리스트를 스스로 통과시키고, 걸리는 항목이 있으면 설계 옵션 비교(2-3 approaches)에 비용 트레이드오프를 명시적으로 포함시킬 것. "동작하는 설계"와 "동작하면서 비용도 목적에 비례하는 설계"를 같은 것으로 취급하지 말 것.
